# 项目分析

> 译自 [project-analysis-skill](https://github.com/Bamzzo/project-analysis-skill)（MIT），基于上游 0d594be（2026-05-28）；中文译文，如有歧义以英文原文为准。

用这个 Skill 把一个陌生或混乱的项目变成清晰、可行动的map。目标不只是总结文件，而是解释这个项目如何工作、核心路径在哪里、什么会坏、怎么验证、下一步做什么。

## 操作原则

- 先观察再下结论。区分代码事实、文档事实、运行时事实、推断和开放问题。
- 优先使用项目真实结构，而不是套用通用架构说法。
- 先找主路径：输入 → 分发 → 核心逻辑 → 外部依赖 → 状态/输出。
- 让不确定性保持可见。未被运行验证时写明"据……推断"。
- 把重要结论与证据绑定：文件路径、命令、测试输出、配置或文档。
- 产出面向行动：下一步该读什么、跑什么、测什么、修什么、避免什么。
- 不要暴露密钥。扫描配置时，只笼统说明存在密钥，不打印具体值。
- 避免逐文件摘要。按角色、流程、边界和风险来解释系统。
- 不要把没读过的文件列进「已检查」清单；宁少报不多报。
- 不要编造 `file:path:line` 证据；拿不准的论断标 Inferred 或 Open。

## 选择深度

用户未指定深度时，使用 **standard**。

对非常大的仓库，即使要求 deep 或 audit，也先做表面地图。

| 深度 | 观察范围 | 执行 | 输出侧重 | 必需证据 |
|---|---|---|---|---|
| **quick** | 顶层文档、清单、脚本、主要目录 | 仅只读探查 | 是什么、可能的技术栈、关键文件、明显风险、下一步命令 | 已检查的文件/命令与主要未知项 |
| **standard** | 文档、清单、配置、入口点、核心模块、测试/CI | 安全的只读命令；仅在明显恰当处做轻量验证 | 架构地图、启动路径、主流程、验证路径、下一步 | 主要论断对应的文件路径，以及实际跑过的命令 |
| **deep** | standard 范围 + 1–3 条高价值流程及其相关测试/契约 | 在安全时做定点测试/构建/类型检查或 dry run | 流程追踪、状态/契约、失败模式、覆盖缺口 | 被追踪路径的文件/行号证据与验证局限 |
| **audit** | 广泛风险面：配置、鉴权、状态、副作用、CI/CD、依赖、测试 | 仅执行校验、dry-run、只读或明确安全的命令 | 证据账本、风险登记、就绪判断、按优先级排序的整改 | 每个主要风险的证据，或显式标注 "Open" |

## 核心工作流

> quick / standard 深度走本工作流；deep、audit 深度或仓库过大时改走「大项目协议」。

1. 必要时先澄清分析目标：
   - 上手、架构报告、调试、重构规划、周报、技术评审或学习路线。
   - 若用户请求已足够明确，直接进行，不要追问。

2. 清点仓库：按下方「只读探查基线」执行，识别语言/框架/包管理文件，以及文档、配置、脚本、测试、CI 与环境模板。

3. 分类项目形态：
   - 单应用、全栈应用、库、CLI、monorepo、Agent 系统、数据/ML 管道、基础设施项目、插件/扩展、移动/桌面应用或混合系统。
   - 只选择与该形态相关的 reference 文件。

4. 定位入口点：
   - 后端：`main`、应用工厂、路由、CLI 入口、包脚本。
   - 前端：包脚本、应用根、路由、API client。
   - Agent/自动化：planner、工具注册表、执行器、状态/观察、模型适配器。
   - 数据/ML：管道运行器、配置加载器、训练/评测/推理入口。
   - 库/SDK：公共导出、包元数据、示例、测试、文档。
   - 基础设施：根模块、stack、清单、部署脚本、CI 工作流。

5. 识别模块与职责：
   - 按角色而非仅按目录分组。
   - 对每个核心模块，记录目的、调用方、依赖、输入、输出与失败模式。

6. 追踪主流程：
   - 记录控制流与数据流。
   - 涵盖外部系统、状态存储、回调、队列、模型调用或文件系统副作用。
   - 非平凡流程用 Mermaid 图。

7. 分析状态与契约：
   - 定位配置、运行时状态、持久状态、缓存、生成文件与重要 id。
   - 识别请求/响应 schema、工具 schema、数据模型、文件格式与错误形状。

8. 评估验证能力：
   - 找出既有测试与测试命令。
   - 识别健康检查、冒烟测试、示例输入、手工验证步骤与缺失测试。
   - 分别记录：实际跑过什么、仅属推断、无法运行的部分。

9. 评估风险与下一步：
   - 把已知问题与潜在风险分开。
   - 按影响与可能性排序。
   - 给出短期、中期、长期建议。

## 只读探查基线

在深入阅读之前，环境允许时先收集一小份安全基线：

- 工作区状态：这是 git 仓库时执行 `git status --short`。
- 文件清单：`rg --files` 或最快的等价手段。
- 顶层结构：`ls`、`dir` 或平台等价命令。
- 项目清单：包、workspace、构建、依赖、锁文件、CI、容器、环境变量模板与 README。
- 脚本面：包脚本、Makefile 目标、任务运行器、CLI 帮助、测试/构建/lint 命令。
- 忽略模式：生成物、vendor、缓存、build、dist、虚拟环境、notebook checkpoint 与依赖目录。

执行脚本前先看内容。不要运行安装、更新、格式化、代码生成、迁移、seed、部署、apply、destroy、写入或触达生产环境的命令，除非用户明确要求，或该命令在当前语境下明显安全。若出现疑似密钥的文件或变量，只描述其作用，不打印值。

## 大项目协议

对庞大或陌生的仓库分阶段推进，避免过早深挖（deep、audit 深度或仓库过大时使用，替代核心工作流）：

1. **表面地图**：按「只读探查基线」收集全仓概况，明确标注将跳过的生成物/vendor 目录。
2. **系统分类**：识别项目类型、运行时边界、包边界、归属边界与可部署单元。
3. **入口地图**：找出每个主要单元如何启动、构建、测试，以及如何与其他单元通信。
4. **核心路径选择**：按用户目标挑选 1–3 条最高价值流程。
5. **证据补全**：为重要论断附加文件路径、命令或运行输出。
6. **验证补全**：适当时运行安全命令；否则列出应运行的确切命令，并说明为何未运行。
7. **综合**：产出按角色组织的架构地图、风险、开放问题与按优先级排序的下一步。

当仓库大到无法完全检查时，说明采样策略与尚未覆盖的区域。

## 默认输出结构

standard 分析产出：

1. 项目概览
2. 技术栈
3. 目录与关键文件地图
4. 启动与运行路径
5. 架构
6. 主要数据/控制流
7. 核心模块
8. 状态与数据契约
9. 外部依赖
10. 测试与验证
11. 风险与开放问题
12. 建议的下一步
13. 新人阅读/学习路径

按用户目的调整该结构。做评审时把风险前置；写周报时把已完成工作与进度前置；调试时把症状、假设与隔离计划前置。

## 证据标签

适当时给论断打标签：

- **Observed（已观察）**：通过阅读文件或运行命令确认。
- **Documented（文档声称）**：文档中写明，但未独立验证。
- **Runtime-verified（运行验证）**：通过命令/测试/API 输出确认。
- **Inferred（推断）**：由结构或命名得出的合理结论。
- **Open（待确认）**：需要用户确认或执行。

对架构、启动、依赖与风险类论断，尽量附证据：

- 代码/配置/文档证据用 `file:path:line`。
- 运行时证据用命令名与输出摘要。
- 无法执行或不安全执行时，写 "not verified" 并说明阻塞原因。

## 完成判据

定稿前，确保分析回答了以下问题，或把它们标为 Open：

- 这个项目是什么、谁/什么在使用它、提供什么价值？
- 如何安装、启动、构建、测试、部署或打包？
- 主要入口点与运行时边界在哪里？
- 最重要的数据/控制流是什么？
- 配置、持久状态、运行时状态、schema 与外部依赖分别在哪里？
- 哪些已由命令或运行时行为验证，哪些仍是推断？
- 最高风险区域、最安全的下一步、最佳新人阅读路径是什么？

## 最后建议

以最高价值的下一步行动收尾。只有当用户清楚"项目是什么、如何工作、下一步看哪里、怎样安全推进"时，这次项目分析才算成功。
