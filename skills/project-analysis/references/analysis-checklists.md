# 分析检查清单

> 译自 [project-analysis-skill](https://github.com/Bamzzo/project-analysis-skill)（MIT），基于上游 0d594be（2026-05-28）；中文译文，如有歧义以英文原文为准。

在仓库分析过程中使用这些清单。除非用户明确要求清单，否则不要原样倾倒；用它们来避免遗漏重要方面。

## 仓库表面

- 项目名称与声明的目的是什么？
- 存在哪些语言与包管理器？
- 顶层目录有哪些？
- 是否有文档、示例、测试、脚本、CI 或部署文件？
- 是否有类似 `.env.example` 的环境变量模板？
- 生成文件、缓存、虚拟环境、构建产物、日志与密钥是否被忽略？
- 仓库看起来是干净的、未完成的、fork 来的，还是被大量改造过？
- 这是单项目、monorepo、嵌套项目，还是混合语言系统？
- 哪些目录因为是生成、vendor、缓存或构建产物而应在分析时跳过？

## 规模与采样

- 仓库小到可以直接完整检查吗？
- 如果不行，使用的是什么采样策略？
- 哪些包/服务/应用的边界在本次范围内？
- 哪些区域被明确排除在本轮之外？
- 哪些文件是脚本、构建、测试与部署的真实来源？
- 是否存在与代码/配置冲突的重复或过期文档？

## 入口点

- 项目在本地如何启动？
- 什么命令运行主服务/应用？
- 哪个文件创建了 app/server/CLI？
- 哪些路由或处理器接收用户/API 请求？
- 有哪些后台 worker、队列或定时任务？
- 哪些命令负责测试、构建、lint 或打包？

## 架构

- 主要分层有哪些？
- 哪个模块处理输入？
- 哪个模块分发工作？
- 哪个模块包含核心领域逻辑？
- 哪个模块与外部系统通信？
- 状态存储在哪里？
- 错误如何表示与传播？
- 哪些组件是可替换的适配器？
- 哪些边界是真实的运行时边界，哪些只是目录组织？
- 哪些组件是公共/稳定的契约，哪些是内部细节？

## 数据与控制流

- 最重要的用户或系统请求是哪一个？
- 它在代码中经过什么路径？
- 每一步转换了什么数据？
- 哪些 id、路径、handle 或状态引用被向下传递？
- 产生了哪些外部副作用？
- 结果如何返回给调用方？

## 状态与契约

- 需要哪些配置？
- 读取了哪些环境变量？
- 哪些 schema 或模型定义输入/输出？
- 读写哪些文件或数据库记录？
- 内存中保留了哪些运行时状态？
- 存在什么缓存或持久化层？
- 哪些数据可能变陈旧？
- 写入之前必须刷新哪些状态？

## 外部依赖

- 第三方 API
- 模型供应商
- 数据库
- 消息队列
- 文件系统位置
- 桌面软件
- 浏览器/运行时依赖
- 操作系统特有功能
- 云服务

对每个依赖，识别：

- 必需配置
- 认证方式
- 失败模式
- 超时/重试行为
- 本地开发替代物或 mock

## 测试与验证

- 有单元测试吗？
- 有集成测试吗？
- 有端到端测试吗？
- 有冒烟测试或示例吗？
- 这些测试在当前环境能跑吗？
- 哪条核心路径没有测试？
- 人如何手工验证这个系统？
- 什么命令能证明项目基本健康？
- 本次分析中实际运行了哪个命令？
- 如果当前执行不安全、太慢或被阻塞，下一步应该运行什么命令？
- 一个通过的结果证明了什么，又没有证明什么？

## 证据质量

- 哪些论断来自代码观察？
- 哪些论断只来自文档？
- 哪些论断经过运行验证？
- 哪些论断是从名称或结构推断的？
- 哪些重要论断缺少证据？
- 在有用处是否附上了文件路径、命令、输出与行号引用？
- 是否在脱敏的前提下仍然描述了密钥的存在与作用？

## 风险扫描

- 配置歧义
- 硬编码路径或端口
- 缺少错误处理
- 隐藏的外部状态
- 非幂等写入
- 破坏性操作
- 弱校验
- 过期文档
- 缺失测试
- 大型无类型载荷
- 模型幻觉或不确定性
- 并发或竞态条件
- 平台特有假设
- 过宽的公共 API 面
- 不清晰的包/服务归属
- 带副作用的构建或部署脚本
- 隐藏在生成代码里的运行时行为
- 本地命令中的类生产默认值

## 新人上手引导

- 第一份该读的文件
- 第一个该跑的命令
- 第一条该测的 API 或 UI 流程
- 第一个小而安全的改动
- 初期不要改的文件
- 改核心逻辑前需要先掌握的概念
- 最适合首次贡献的模块
- 在理解架构之前应避开的高风险模块
