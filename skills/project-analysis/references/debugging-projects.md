# 调试导向的项目分析

> 基于 [project-analysis-skill](https://github.com/Bamzzo/project-analysis-skill)（MIT）commit 0d594be（2026-05-28）改编，含内容修改与增补。

当用户目标是理解一个 bug、失败的安装配置、断裂的集成、不稳定的工作流或令人困惑的运行时行为时使用。

## 调试第一性原理

- 先复现再修复。
- 把问题缩减到最小的失败路径。
- 把症状与原因分开。
- 一次只改变一个主要变量。
- 用原始症状验证修复。
- 保留用户改动，避免无关重构。

## 失败边界问题

- 请求/动作是否开始了？
- 是否到达了第一道边界？
- 每一层是否收到了预期的输入？
- 每一层是否产出了预期的输出？
- 第一个可观察到的偏差在哪里？
- 失败是确定性的吗？
- 它以前能正常工作吗？
- 最近改了什么？

## 常见层次

```text
用户输入
UI/client
网络
API 路由
控制器/服务
数据/模型层
外部依赖
运行时环境
输出/渲染
```

对每一层问：

- 输入存在吗？
- 输入形状正确吗？
- 处理器被调用了吗？
- 输出存在吗？
- 错误被记录了吗？
- 是否超时或被取消？

## 要收集的证据

- 确切命令
- 确切错误
- 失败时间点附近的日志
- 脱敏后的配置值
- 环境版本
- 分支与工作区状态
- 最小输入
- 期望输出 vs 实际输出
- 最近的改动

## 隔离计划

1. 校验环境与配置。
2. 运行健康检查。
3. 直接调用失败的 API/工具。
4. 尽可能用 mock 替换真实外部依赖。
5. 测试最小的内部函数。
6. 逐层把链路接回来。
7. 跑原始的端到端路径。

## 修复策略

优先：

- 最小化的定点改动。
- 根因不确定时，先补更好的诊断信息。
- 修复前失败、修复后通过的测试。
- 针对安装/配置类问题更新文档。

避免：

- 调试期间做大范围重写。
- 在没理解的情况下吞掉错误。
- 把命令成功退出当作用户可见行为正常的证据。
- 在检查本地配置与数据流之前就把锅甩给模型/框架。

## 验证计划

包含：

- 运行的命令/测试
- 必要时的手工冒烟测试
- 预期可观察的结果
- 回归风险
- 残余未知项
